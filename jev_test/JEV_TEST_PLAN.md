## 요약 — 한눈에 보기

**무엇을 묻나**: "한국어 업무형 데이터의 **정답지 기준으로**, 이 AI 에게 어디까지 자동으로 맡길 수 있는가."
사람이 정답을 다시 확인하지 않는다 (사용자 결정 10-13). 그래서 결과는 "실제 업무에서 오류 몇 %" 가 아니라 "이 정답지 기준으로 오류 몇 % 이하" 다 (§4-2).

- **결정 모델**은 글을 쓰지 않고 **객관식 답 + 확신 정도**만 낸다. 예: 고객 문의 → "환불 92% · 배송 6% · 기타 2%".
  프로그램이 그 숫자를 보고 자동 처리하거나 사람에게 넘긴다.
- 이 폴더(`jev_test/`)는 **앞으로 나올 결정 모델 전부를 시험하는 공용 틀**이다. 등록된 모델은 전부 돌린다.
  처음 등록: Cloudflare **Clef** · **Clef-Flash**, Perplexity **pplx-decider v1** · **v1.1**.
- **세 가지를 잰다**: ① 잘 맞히나 ② "90% 확신" 이 진짜 90% 인가 ③ **오류를 1·2·5% 이하로 지킬 때 몇 % 를 사람 없이 처리할 수 있나** (주 지표 — 사전 선언: KoSGD 2%).
- **시험 문제**: 공개 한국어 업무형 벤치마크 6종 (예약 대화 · 챗봇 도구 판단 · 댓글 검수 · 상담 연결 · 금융 뉴스 · 문서 기반 답변). 정답을 만든 방식은 셋마다 다르다 — 주 지표인 KoSGD 는 **시뮬레이터가 만든 주석**이다 (§3 A).
- **첫 실행**: A 묶음 + B1 만. 나머지는 무엇을 확인하려는지 적은 뒤 후속으로 (§7).
- **비교 대상**: 같은 뿌리의 일반 AI(Qwen3.8-27B)를 그냥 쓸 때, 더 싼 분류기(임베딩 + 로지스틱 회귀)를 쓸 때.
- **순서**: 준비(P0) → 코드(P1) → 서빙 검증(P2) → 본시험(P3) → 속도(P4) → 보고(P5).

## 1. 배경 — 결정 모델과 질문 형식

Jev(TypeSafe AI, 2026-09-15 early access)가 처음 내놓은 형식을 오픈웨이트 모델들이 따른다. 요청은 `POST /v1/systemone`.

```json
{"state": "<상황: 문자열 또는 JSON>",
 "questions": {"<질문 ID>": {"type": "noul | choice | score", "instructions": "...", "criteria": {...}}}}
```

| 질문 종류 | 의미 | 선택지 | 응답 |
|---|---|---|---|
| `noul` | 참/거짓 | `true`/`false` (설명 선택) | P(true) |
| `choice` | 객관식 | 선택지 ID → 설명 | 선택지별 확률 |
| `score` | 순서 있는 등급 | 설명 목록 (0 부터) | 단계별 확률 + 기대 점수 |

한 요청에 질문을 여러 개 묻는다. 모델에 따라 질문을 **함께** 채점하기도(Clef) **따로** 채점하기도(pplx) 한다.

| `clef_flash` | `Cloudflare/clef-flash` (`8b2e5fd`) | Qwen3.5-9B | ~19GB | 함께 (같은 코드) | 같음 | 같음 |
| `pplx_v1_1` | `perplexity-ai/pplx-decider-v1.1-27b` (`6195aa5`) | Qwen3.8-27B | ~52GB BF16 | **따로** (readout + 저장된 temperature 1.00874, noncausal) | SGLang (PR #42645, 10-08 병합 — **GB300 만 검증, SM120 경로 미실행**) | `source/src/autojev` |

모델별 주의 (확인된 사실):
- **Clef**: 입력 상한은 인코딩 전체 16,384 토큰(카드 코드 기본값), 넘으면 **state 꼬리를 조용히 잘라낸다**. Cloudflare 블로그는 "64k" 라고 쓴다 — P0 에서 확인. choice 는 **선택지 ID 순으로 정렬**해 넣는다.
- **토크나이저**: Clef·Clef-Flash 가 같은 파일, pplx v1·v1.1 이 같은 파일, 둘 다 저장소의 Qwen3.8-27B 사본과 파일은 다르다 (10-12 sha256 비교). 위 구성의 요청 길이는 세 파일에서 같게 나왔다.
- **pplx**: 참조 구현은 decision 전체 8,192 토큰을 넘으면 **거부**한다. choice ≤255, score 2–10 단계. temperature 는 **정확히 한 번** 적용해야 한다. 학습 데이터에 tasksource 포함.

### 2-2. 새 모델 추가 계약

1. `configs/models/<id>.yaml` — 리포 sha · 서빙 방법(이미지·명령) · `/v1/systemone` 주소 · 입력 상한과 넘칠 때 동작(잘림/거부) · 질문 채점 방식(함께/따로) · 공개 점수(있으면).
2. `serving/<id>.sh` — §6 서버 점유 절차를 따르는 기동·정지 스크립트.
3. **T0 서빙 게이트**를 통과해야 본시험 결과가 집계에 들어간다. 참조 구현이 없는 모델은 확률 대조를 못 하므로 결과에 **"T0 부분 통과"** 로 표시한다.
4. 그 모델의 백본 LLM 이 저장소에 설정돼 있으면 비교 기준 B1 을 함께 돌린다 (Clef-Flash 의 Qwen3.5-9B 는 현재 설정이 없어 B1 생략).

### 2-3. 비교 기준 (baseline)

| ID | 방식 | 쓰는 곳 | 해석 |
|---|---|---|---|
| **B1** | 같은 백본 LLM 의 **logprob** — 질문마다 호출 1번, 선택지에 단일 토큰 라벨, `allowed_token_ids` 로 제한, 유효 후보로 재정규화. **chat + 생각 끔** 필수 (Qwen 템플릿이 `<think>` 를 열면 보기 확률이 무너진다 — KMMLU 에서 두 번). 세부 계약은 아래 | 모든 셋 | "백본을 그냥 쓰면 어떤가" 하는 **운영 대안**. head·attention·프롬프트·보정이 함께 다르므로 "후학습만의 효과" 로 해석하지 않는다. 대상: Qwen3.8-27B **BF16** (`foundation_model_test_non_thinking/configs/models/qwen_qwen3.8_27b.yaml`, 엔진 vLLM — line 23), FP8 은 별도 열 |
| **B2** | 임베딩 + 로지스틱 회귀 (MTEB Classification 방식) | **학습 split 이 있는 고정 라벨 셋만** (K-MHaS · KOTE · KorFin-ASC · KLUE-MRC 등) | 해당 과제 라벨로 학습한 **지도학습 참고치**. 결정 모델은 처음 보는 상태라 "대안이 더 싸다" 결론에는 학습 데이터가 필요하다는 단서를 붙인다. KoSGD·FunctionChat 처럼 선택지가 요청마다 바뀌거나 학습 split 이 없으면 B2 를 내지 않는다. KorFin 은 한 문장에 종목(aspect)별 정답이 여럿이라 입력을 `(SRC, ASPECT)` 로 조건화하고 분할은 문장 단위로 한다 |

**B1 계약 (개정 12, vLLM 0.19.0 기준 — 10-13 실서버는 0.28.0, 아래 서버 옵션 두 개가 실제로 필수임을 확인: 없으면 400·라벨 누락, P1 계약 §10)**:
- **라벨**: `A–Z · a–z · 0–9` 62개 — Qwen3.8 토크나이저에서 모두 단일 토큰·서로 다른 ID (10-13 확인. 숫자 `0`–`38` 은 10개만 단일 토큰이라 쓰지 않는다). 선택지 60개(MASSIVE)까지 된다. 라벨 대응표와 토크나이저 해시를 동결하고, chat 템플릿의 답 위치에서도 단일 토큰인지 P0 에서 본다. 선택지 편향 검사(§4-5)는 이 62개 안에서 대응을 재배정한다.
- **서버**: `--logprobs-mode processed_logprobs --max-logprobs 64`. 기본값(`raw_logprobs`, 20)이면 허용 토큰 마스크 **전** 전체 어휘의 상위 20개가 와서 보기가 빠진다 — v0.19.0 `vllm/v1/sample/sampler.py` 에서 raw 는 82행에서 계산되고 마스크는 그 뒤(92 → 288행), processed 는 마스크 뒤 `sample()` 에서 계산된다 (소스 확인, 실서버 미확인).
- **요청**: `max_tokens=1`, `logprobs=true`, `top_logprobs ≥ 선택지 수`, `temperature=1`, `top_p=1`, `top_k=-1`, `min_p=0`, repetition penalty 1, frequency·presence penalty 0, logit bias·bad words·추가 processor 없음. 명시하지 않으면 모델 `generation_config` 기본값(top_k 등)이 들어와 후보가 잘린다.
- **답**: 돌아온 후보 분포의 **argmax** (choice 는 동률이면 라벨 순서가 앞인 것. **noul 은 p(true) ≥ 0.5 → true** — 대응을 바꾸는 선택지 편향 검사에서 동률 답이 라벨 위치로 바뀌지 않게, 개정 13). temperature=1 이라 샘플된 토큰은 답이 아닐 수 있어 쓰지 않는다. 모든 후보가 유한값으로 돌아왔는지 요청마다 검사하고, 빠지면 `error` 로 센다.
- **비용 보고**: 운영 대안이므로 정확도·위험과 함께 **논리 요청 단위 완료 지연·실패율·호출 수·입력 토큰 수**를 같은 하드웨어에서 잰다 (KoSGD 전체판 요청 1개 = 호출 12번). 엔진이 결정 모델(SGLang)과 다르다는 점은 운영 구성의 차이로 표에 적는다. T2 의 모델 간 지연 표에는 넣지 않는다 (엔진·부하 형태가 다르다).
- **진입 조건 (P0, 실서버)**: 배포 버전 0.19.0 · 위 실효 설정 · chat 엔드포인트가 `top_logprobs=64` 를 받는지 · 마스크된 토큰(−9999 등) 처리 · 모든 후보 반환.

## 3. 시험 트랙

### T0 · 서빙 게이트 — "우리 서버가 개발사와 같은 확률을 내는가"

정확도 재현만으로는 부족하다 — logit 을 상수로 나눠도 정답 순위·F1 은 같고 보정 지표만 바뀐다 (pplx temperature 누락·중복을 못 잡는다).
pplx 의 temperature 는 1.00874 라서, 누락이나 중복이 만드는 확률 차이가 2지선다에서 최대 약 0.0019 다 (10-13 계산 — 0회↔1회, 1회↔2회 모두). 이 차이가 T0 허용폭보다 작을 수 있으므로 **C1 의 temperature 경로 검사**(§8)가 따로 잡는다. T0 비교도 유지한다 — 단위 검사는 서빙 경로가 그 함수를 실제로 쓰는지 보장하지 않는다. 두 검사의 검출 범위를 결과에 함께 적는다.

1. **확률 대조 (필수)**: 고정 fixture(세 질문 종류 · choice 2/8/16 · 한국어 선택지 · 질문 8개 묶음 · 긴 state)를 **리포 참조 구현**과 **SGLang 서버**에 똑같이 넣어 분포 최대 절대차·답 변경률을 본다.
   허용폭은 P0 에서 **참조 구현을 배치 구성만 바꿔 반복 실행한 변동**으로 정해 이 문서에 적는다 (카드·SGLang 문서 모두 배치·커널에 따라 확률이 조금 흔들린다고 적는다).
   긴 state fixture 는 유지한다 — **상한+1 토큰 입력이 거부 또는 잘림으로 기록되는지** 를 §2-2 의 '넘칠 때 동작' 과 대조한다 (본시험 입력은 상한보다 훨씬 짧아 이 동작을 T0 에서만 본다).
2. **공개 수치 회귀 (보조)**: [Decision Index](https://github.com/apolinario/decision-index) 키트 HTTP 엔진, **`--edition 0.2.1` + 키트 commit · suite hash · scorer 고정** (기본판은 0.3).
   후보 (pplx 는 `skill` 이 아니라 `raw×100` 과 비교, ID↔이름 매핑은 P0 에서 키트로 재확인):

   | ID | 벤치 (macro-F1) | Clef 카드 | pplx v1.1 raw |
   |---:|---|---:|---:|
   | 4 | BANKING77 | 94.2 | 80.57 |
   | 5 | CLINC150+OOS | 97.4 | 91.52 |
   | 11 | ContractNLI | 81.4 | 78.38 |
   | 12 | ANLI | 69.8 | 74.28 |
   | 39 | FinEntity | 96.2 | 95.42 |

   차이가 P0 에 고정한 기준을 넘으면 멈추고 원인을 찾는다. 이것은 **회귀 신호**이지 성능 결론이 아니다.
   라이선스: ANLI CC BY-NC 4.0, FinEntity 미기재 — 내부 평가만. HLE 는 빌드에서 뺀다.

### T1 · 본시험 — 결정 정확도·보정·자동 처리 범위

#### A. 업무 결정 (핵심, 한국어, 공개 라벨)

원래 라벨을 **한 요청에 질문 여러 개**로 재구성한다. "성공 판정 질문" 은 요청 성공(전부 맞아야 성공)과 확신 점수에 들어가는 질문, "진단 질문" 은 함께 묻되 성공 판정에서 빼는 질문이다.
진단 질문은 오류·확신 계산에서 빠질 뿐 **입력에서는 빠지지 않는다** — 질문을 함께 채점하는 Clef 에서는 진단 질문이 성공 판정 질문의 출력에 영향을 줄 수 있다. 그래서 진단 질문 구성은 판마다 동결하고, 결과는 "이 질문 구성에서의 성공 판정" 으로 해석한다.

**라벨 출처 (개정 12)**: KoSGD(= 영어 SGD 의 번역)의 행동·진행 중인 일 라벨은 **시뮬레이터가 대화 뼈대와 함께 만든 주석**이고, 사람은 템플릿 문장을 자연스럽게 바꿔 쓰기만 했다 ([SGD 논문](https://ar5iv.arxiv.org/html/1909.05855) §3). 그래서 바꿔 쓴 문장이 주석과 어긋날 수 있고, 한국어는 번역체다. 나머지 셋의 라벨 생성·검수 방식은 `datasets.yaml` 의 `label_source` 에 셋마다 적는다 (확인 전에는 "사람이 독립 판정" 이라고 쓰지 않는다).

| 업무 | 셋 | 상황(state) | 성공 판정 질문 | 진단 질문 | 평가 요청 | 묶음 단위 |

- **KoSGD 세부** (개정 11):
  - 행동 목록은 이 데이터의 act 11종 전부로 동결한다 (성공 판정 8 + 진단 2, GOODBYE·THANK_YOU 는 하나로).
  - **서비스 목록은 대화에서 가져오지 않는다.** 대화의 `services` 필드는 그 대화의 **미래** 서비스까지 담아 정답 힌트가 된다. 대신 test 스키마의 서비스 21개·의도 38개를 이름과 설명만 남겨 **모든 요청에 같은 바이트로** 넣는다. 의도 선택지 ID 는 `서비스/의도` 다 (서비스가 달라도 이름이 같은 의도가 4개 있다).
  - **진행 중인 일 칸 2개**: 한 턴의 frame(서비스)은 최대 2개다 (3,000 턴 중 1개 2,744 · 2개 256). 정답은 그 턴 frame 들의 `active_intent` 중 `NONE` 이 아닌 것의 집합이고, 모자란 칸은 `NONE` 이다.
    - 정답은 **이번 턴 frame 에 있는 서비스**만 담는다 — 앞 턴에만 있던 서비스는 빠진다 (예 `12_00101` turn 6). 그래서 문구는 "이 턴까지" 가 아니라 **"고객의 이번 발화와 관련된 서비스에서 지금 진행 중인 일"** 로 쓴다 (10-13 Codex 지적, 동결 전 수정 — 사유 '두 가지로 읽힘').
    - 문구에는 "①·②에 서로 다른 일을 서비스 목록 순서대로, 없으면 `NONE`" 이라고 적는다. 칸을 따로 채점하는 모델(pplx)도 두 칸을 구분할 수 있게 하려는 규칙이다.
    - **채점은 순서를 따지지 않는다**: 두 칸의 답 묶음이 정답 묶음과 같으면 맞다. 같은 의도를 두 칸에 쓰면(`NONE` 제외) 틀리다. 채점은 정답을 읽지만 수락 판단(확신 점수)에는 쓰지 않으므로 새지 않는다.
    - 모든 칸을 채점하므로 채점 마스크가 비지 않는다 ($M_i = J_i$).
  - **두 판**: 전체판(칸 2 + 행동 8)과 행동판(행동 8). state 는 두 판이 같다. pplx 는 질문을 따로 채점하므로 행동판 점수를 전체판 출력에서 계산한다. Clef 는 함께 채점하므로 행동판을 따로 돌린다.
  - **주 지표 판 (사전 등록, 모델 실행 전 감사 v3 결과로만 정한다)**: 감사 v3 의 R2v3·R4·R5·R6·R7 이 모두 PASS 면 **전체판**, 하나라도 FAIL 이면 **행동판**이 주 지표다. 다른 판은 참고 표다. 결과를 본 뒤 판을 바꾸지 않는다.
  - **앞 턴 베끼기 비교 기준 (직전 정답을 아는 지속성 기준)**: 직전 USER 턴의 **정답** 진행 중인 일 집합을 그대로 답으로 쓴다 (첫 USER 턴은 `NONE`). 모델은 대화와 서비스 목록만 받으므로 이 기준은 **모델이 모르는 정보(직전 정답 상태)를 쓴다** — 배포 가능한 무비용 대안이 아니라 "진행 중인 일이 얼마나 이어지는가" 를 보여 주는 참고선이다. 확률이 없어 처리율은 못 내고, 칸 묶음 정답률만 나란히 낸다.
  - "현재 서비스만" 넣는 입력은 정답(frame 서비스)을 흘리므로 쓰지 않는다.

## 4. 채점 규칙

### 4-1. 지표

| 무엇 | 지표 | 규칙 |
|---|---|---|
| 맞췄나 | 질문별 macro-F1, 클래스별 재현율 | 정답률(accuracy)은 제목 지표로 쓰지 않는다 (불균형 셋) |
| 확률을 믿을 수 있나 | ECE(15 등폭 bin, **bin별 건수·정확도·평균 확신 함께**), Brier(one-hot 제곱합 평균), log loss(`[1e-12,1]` clip) | 각 모델이 **배포한 그대로의 확률** (pplx 는 temperature 적용 후). 선택지 수가 다른 질문끼리 평균하지 않는다. KorSTS 처럼 정답이 실수인 셋은 이 행이 아니라 '등급' 행으로만 낸다 |
| **자동 처리 범위 (주 지표)** | **위험 고정 처리율** (§4-2 정의) | 요청 단위. 셋마다 "요청당 성공 판정 질문 수" 를 같은 표에 적고, **셋끼리 처리율을 평균하지 않는다** (질문이 많을수록 "전부 맞아야 성공" 이 어렵다) |
| 등급 | 기대 점수 vs 실수 정답 Pearson · Spearman · MAE | KorSTS (반올림하지 않는다) |
| 모델 간 차이 | **묶음 단위 paired bootstrap 95% CI** | 처리율·F1 차이에만. 위험 상한에는 쓰지 않는다 (오류 0 표본을 재표집하면 상한이 0 이 된다) |

결과는 **"이 벤치마크 라벨 기준의 요청 단위 자동 판단률"** 로만 해석한다 — 예: KOTE 감정 판단은 실제 상담원 연결의 정답이 아니다.

**출력 계약 (개정 12 — 지금 동결, P0 결과를 보고 바꾸지 않는다)**:
- 주 지표의 확률·확신 점수는 **API 가 돌려준 값 그대로**다. Clef 참조 구현은 모든 확률을 **소수 넷째 자리로 반올림**한다 (`joint_schema_model.py:526–534`) — 반올림된 값은 log 로 바꿔도 복구되지 않는다. 그래서 확신 점수 1.0 동률이 많을 수 있고, 동률은 §4-2 규칙대로 **묶음째 수락하거나 수락하지 않는다**. 그 결과 NO_THRESHOLD·UNDERPOWERED 가 나오면 그대로 보고한다 — 그것도 "운영에서 이 API 로 재현할 수 있는 처리율" 이다.
- **choice 의 답 $\hat y$ 는 API 의 `choice` 필드**다. Clef 는 반올림 **전** 확률의 argmax 로 `choice` 를 정하므로, 반올림된 확률표의 argmax 와 다를 수 있다 (예: 0.49996 / 0.50004 → `choice`=B, 확률은 둘 다 0.5). 확신 점수는 `confidence`(= 그 `choice` 의 반올림 확률)다. `choice` 필드가 없는 모델은 확률표 argmax, 동률이면 선택지 ID 순서가 앞인 것.
- **원시 응답을 요청마다 그대로 저장**한다 (C5 재채점의 입력). 분포 검증기의 '합 = 1' 은 반올림 허용오차(선택지 수 × 5e-5)로 본다.
- 반올림 전 값(logit·log 확률)은 받을 수 있는 모델에서만 **진단 열**로 낸다. 결정 모델 채택 조건으로 올리는 것은 이번 판에서 하지 않는다 (사용자 결정 10-13).
- 같은 시험 표본에서 결과가 가장 좋은 모델을 고르면, 고른 모델의 상한은 95% 보장이 아니다 (모델 4개). 인증은 **모델별**로만 말하고, 모델을 고른 뒤 그 모델의 위험을 주장하려면 새 확인 표본이 필요하다.

### 4-2. 위험 고정 처리율 — 정의

요청 $i$ 의 성공 판정 질문 집합 $J_i$, 질문별 확률 $p_{ij}$, 채점 마스크 $M_i \subseteq J_i$ (정답이 있는 질문):

- 요청 오류 $\ell_i = \mathbf 1\{\exists j \in M_i : \hat y_{ij} \ne y_{ij}\}$ — 예외: KoSGD 진행 중인 일 두 칸은 묶음 하나로 비교한다 (순서 무관, §3 KoSGD 세부). 확신 점수에는 두 칸이 각각 들어간다
- 확신 점수 $s_i = \min_{j \in J_i} \max_c p_{ij}(c)$ — **$J_i$ 전체** 로 계산한다 (마스크 $M_i$ 는 정답에서 오므로 수락 판단에 쓰지 않는다). choice 의 질문 확신은 §4-1 출력 계약대로 API `confidence` (= 그 `choice` 의 확률) 다 — 확률표의 최댓값보다 작으면 `choice_not_argmax` 경고로 센다 (개정 13)
- 유효 응답 $v_i$ (거부·잘림·오류가 아님), 수락 $a_i(t) = v_i \cdot \mathbf 1\{s_i \ge t\}$
- 표본 $S$ 에서 수락 수 $n_S(t) = \sum a_i$, 수락 중 오류 $k_S(t) = \sum a_i \ell_i$
- 처리율 $\hat C_S(t) = n_S / |S|$ — **분모 $|S|$ 는 처음 뽑은 요청 전부** (거부·잘림·길이 초과 포함)
- 단측 Clopper–Pearson 95% 상한 $U(k,n)$ — 이 순서로 판정: $n=0$ 이면 정의하지 않음(처리율 0, 위험 N/A) · $k=n$ 이면 1 · $k=0$ 이면 $1-0.05^{1/n}$ · 그 밖에는 $\mathrm{Beta}^{-1}(0.95;\,k+1,\,n-k)$
- noul 질문의 $\max_c p_{ij}(c)$ 는 $\max(p, 1-p)$ ($p$ = P(true)). 채점 마스크 $M_i$ 가 빈 요청은 위험 표에 넣지 않고(**분모 $|S|$ 에서도 뺀다**) 건수를 따로 적는다 — 첫 실행 6셋에서는 0 건 (10-13 집계).
- $v_i$ 의 '잘림' 은 §4-4 의 세 경우 중 어느 것이든이다. Clef 는 잘라도 알리지 않으므로, **요청 길이 > 그 모델의 실측 상한이면 잘림으로 본다** (자기 토크나이저·직렬화 기준) — 원래 정의보다 넓은 **보수적 대리 기준**이다. 서비스 목록·도구 목록도 판단 입력이므로 꼬리만 잘려도 유효 응답이 아니다.

목표 위험 $\tau \in \{1\%, 2\%, 5\%\}$ 마다:

1. **개발 표본 (임계값 고르기만)**: 후보 $t$ = 개발 확신 점수의 서로 다른 값. 사전 고정 규칙 —
   경험 위험 $k_D/n_D \le \tau/2$ 를 만족하는 $t$ 중 개발 처리율이 가장 큰 것, 동률이면 큰 $t$. 없으면 **NO_THRESHOLD**.
   ($\tau/2$ 여유는 시험에서 인증될 여지를 남기려는 사전 상수다. 인증의 타당성에는 영향이 없고 검정력에만 영향이 있다 — 개발 표본이 작으면 사실상 '개발 오류 0' 조건이 되어 고른 임계값의 수락 수가 작고, 시험에서 **UNDERPOWERED** 가 되기 쉽다. 예: KoSGD 2% 를 MEETS 로 받으려면 시험 수락이 대략 600 건(처리율 25%) 이상 필요하다(오류 6 건 기준). 개발 처리율·위험은 결과로 쓰지 않는다.)
2. **시험 표본 (인증)**: $t^*$ 를 시험 점수를 보기 전에 파일로 고정한 뒤
   - $n_T < n_{\min}(\tau)$ → **UNDERPOWERED** ($n_{\min}$ = 오류 0 일 때 $U \le \tau$ 가 되는 최소 수락: 1% 299 · 2% 149 · 5% 59)
   - $U(k_T, n_T) \le \tau$ → **MEETS** (처리율 $n_T/|T|$ 보고)
   - 그 외 → **FAILS** (경험 위험만 $\tau$ 이하여도 FAILS)
   - 시험에서 실패해도 임계값을 다시 고르지 않고, 사후에 $\tau$ 를 추가하지 않는다.
3. 모든 칸을 (상태, 처리율, $k$, $n$, $U$) 로 낸다. 셋 이름으로 수준을 미리 빼지 않는다. 다만 **시험 묶음 수 $|T| < n_{\min}(\tau)$ 인 칸은 모델과 관계없이 MEETS 가 불가능**하므로 "표본 부족(원리적)" 으로 따로 표시한다 (예: FunctionChat 시험 86 묶음 → 1·2% 는 원리적 부족, 5% 만 가능).
4. $b_{\rm flip}$ 은 MEETS 칸에서만 계산하고, 다른 상태는 N/A. NO_THRESHOLD 칸은 처리율 0 · $k,n,U$ N/A 로 낸다.
5. `summary.json`(최상위 집계 호환, P1 계약 §8-3) 의 `score` 는 **인증된 처리율**이다 — MEETS 칸만 $n_T/|T|$, FAILS·UNDERPOWERED·NO_THRESHOLD 는 0. 위 3 의 (상태, 처리율, $k$, $n$, $U$) 는 같은 파일의 `status`·`coverage_observed`·`k_errors`·`n_accepted`·`U` 에 상태와 무관하게 그대로 적으므로, 처리율은 `coverage_observed` 로 읽고 `score` 를 처리율로 읽지 않는다 (10-16 개정; 그 전 코드는 FAILS 에 관측 처리율을 `score` 로 냈다).

- **주 지표(사전 선언)**: KoSGD, $\tau = 2\%$ — 모델별 상태와 처리율. 나머지 칸은 기술 통계이며 "모두 통과" 같은 동시 주장은 하지 않는다. KoSGD 라벨은 시뮬레이터 주석이므로 주 지표도 "그 주석 기준" 이다 (§3 A 라벨 출처).
- **정답지 기준 인증 (개정 11 — 라벨 관문 폐지, 사람 재라벨 없음)**: 1·2·5% 칸을 모두 같은 방식으로 연다. 인증 대상은 **"동결한 재구성 규칙과 벤치마크 라벨에 대해, 고정 임계값에서 수락된 요청의 오류율 상한이 $\tau$ 이하인가"** 다.
  - 실제 위험은 모델 $m$ 이 수락한 요청 안의 라벨 오류율 $\epsilon_m = P(\text{라벨} \ne \text{참값} \mid \text{수락}_m)$ 만큼 다를 수 있다. $\epsilon_m$ 은 모델마다 다르고(수락 묶음이 다르다) 측정하지 않는다. 라벨 오류가 모든 모델에 같은 문항이라도 순위가 보호되지 않는다 — 틀린 라벨을 따라 한 모델은 점수를 얻고, 맞는 답을 낸 모델은 잃는다.
  - **판정 여유**: 칸마다 $b_{\rm flip} = \min\{b : U(k+b,\,n) > \tau\}$ — "수락 중 정답 처리된 몇 건이 오류로 바뀌면 MEETS 가 깨지는가" 를 같이 적는다. 예: $n=150, k=0$ 이면 2% 를 통과하지만 $b_{\rm flip}=1$ 이다.
  - **판본 비교 (KoSGD) — 표를 내지 않는다**: 감사 v3 에서 우리가 쓰는 정답(행동 종류·진행 중인 의도)이 영어 SGD 와 USER 턴 42,297 개 전부에서 같았다 (KoSGD 의 주석 수정은 슬롯 쪽에만 있다 — Claude 직접 집계 10-13). 다시 채점해도 결과가 같으므로 민감도 표는 정보가 없다. 같은 이유로 '두 판이 일치' 는 라벨이 맞다는 증거가 아니다.
  - LLM 재판정으로 사람을 대신하지 않는다 (백본과 오류가 상관되고, "실제 위험" 으로 오해된다).
- 시험에서 MEETS 를 받아도 수락된 요청의 클래스·서비스·질문 수 분포와 클래스별 위험을 함께 낸다 (쉬운 클래스만 처리했는지 보이게).
- **진단 질문의 수락 내 오류율**: 성공 판정에서 뺀 질문(KoSGD AFFIRM_INTENT·NEGATE_INTENT 등)도 수락된 요청 안에서 틀린 비율을 함께 낸다 — 특히 NEGATE_INTENT(제안된 작업 거절)를 놓치면 원하지 않는 작업이 실행될 **수 있다** — 이 평가는 실제 실행을 보지 않으므로 측정한 피해가 아니다. 해당 턴: NEGATE_INTENT 78/3,000 = 2.6% · AFFIRM_INTENT 68/3,000 = 2.3% (겹침 0. 개정 11 의 "146 = 4.9%" 는 둘을 더한 값이었다).

### 4-3. 표본 나누기

- **인증 모집단 (개정 12)**: 셋마다 동결한 **평가 풀의 묶음 균등 분포**다. 위험 상한은 "이 풀에서 묶음을 하나 무작위로 고르고 그 대표 요청을 냈을 때의 오류율" 에 대한 것이고, 미래 요청 일반이나 행 균등 분포에 대한 것이 아니다.
- **추출 순서** (셋마다 `datasets.yaml` 에 적고 코드가 그대로 따른다):
  1. 평가 풀 만들기 — 원본 split 에서 cap 이 있으면 고정 seed 표본. 층화 cap 이면 **층별 할당 수를 표로 적는다** (비례가 아니면 풀은 층 혼합이고, 상한도 그 혼합에 대한 것이다).
  2. 묶음 정하기 — 셋마다 묶음 키 (KoSGD 대화 · FunctionChat 시나리오 연결요소 · KorFin 문장 · KLUE-MRC 문맥 · 그 밖에는 문장).
  3. 대표 고르기 — 묶음당 요청 하나를 고정 seed 로 (KoSGD 대화당 USER 턴 1개, KLUE-MRC 문맥당 질문 1개, FunctionChat 묶음당 1행).
  4. 나누기 — 묶음 ID 를 고정 seed 로 섞어 앞 $\lfloor 0.2G \rfloor$ 개를 개발, 나머지를 시험으로 ($G$ = 묶음 수). 층화 분할은 하지 않는다.
- 이항 상한을 쓰는 표는 묶음당 요청 하나다. 묶음보다 잘게 쪼개 세지 않는다 (묶음 안의 오류는 서로 상관돼 독립 가정이 깨진다).
- 층별(클래스·서비스·질문 수) 결과는 **진단**으로만 내고 인증하지 않는다.
- KLUE 는 test 정답 비공개 → validation 을 평가 풀로 봉인. B2 학습은 train 에서만, 평가 풀과 같은 묶음 제외.

### 4-4. 실패·잘림·길이

- **문항을 길이로 빼지 않는다.** 길이 초과·거부·잘림·오류는 그 모델의 **자동 처리 못 함** — 처리율 분모에 남고 오류로 세지 않는다.
- **잘림은 세 경우로 나눠 기록한다**: ① 질문 대상 발화가 잘림 ② 발화는 남고 꼬리(서비스 목록·도구 목록)만 잘림 ③ 상한을 넘었는데 모델이 정상 응답을 줌 (Clef). 셋 다 $v_i = 0$ 이다. 운영에서도 같은 길이 검사로 사람에게 넘긴다는 전제를 결과에 적는다 — 운영이 ③ 의 응답을 그대로 쓰면 그 오류는 이 위험 표 밖에 있다.
- 상태 기록: `ok / rejected / truncated / error / retried` — 재시도 횟수와 논리 요청 수를 구분.
- **맞췄나·보정**: 확률이 있는 문항만 쓰고 제외 건수를 옆에 적는다. 별도로 **공통 코호트 표**(모든 모델이 `ok` 인 문항)를 낸다.
- **길이 판정은 모델마다 자기 토크나이저·직렬화로** 한다. 모델별 상한 $L_m$ 은 P0 실측값 (잠정: pplx 8,192, Clef 16,384 — 블로그 64k 는 실측 전 채택하지 않는다). 길이 구간(≤4k · 4–8k · 8–16k · >16k)별 처리율도 낸다 — 10-12 측정으로는 거의 전부 4k 이하다.
- 입력 순서: 질문 대상 발화가 잘리지 않게 **대화를 앞, 스키마·도구 목록을 뒤**에 둔다 (Clef 는 state 꼬리를 자른다).

### 4-5. 구조 차이 검사 (잘리지 않는 조건에서만)

- **질문 묶음 효과**: KoSGD·K-MHaS 에서 (묶음 크기) × (질문 순서 2가지) × (무관 질문 추가 유/무). "따로 채점" 모델(pplx)은 의미상 독립의 대조군 (내부 8개 배치라 비트 단위 0 은 아님).
- **선택지 편향**: 선택지 ID 자체를 바꾼다 (재배정, 영문 ↔ 한국어 ID) — Clef 는 ID 순 정렬이라 JSON 순서만 섞으면 입력이 같다. B1 에도 같은 검사.

### 4-6. 문구·라벨 체계 동결 절차

- 질문 문구 · 선택지 설명 · 행동/감정 목록 · 직렬화 · 분할 ID · §4-2 의 임계값 규칙 · §4-1 출력 계약 · B1 라벨 대응표를 **평가 풀 문항으로 모델을 처음 돌리기 전에** `configs/tasks/*.yaml` 로 커밋하고 해시를 C5 재현 지문에 넣는다. `tasks/` 커밋 시각이 `results/` 의 어떤 파일보다 앞서야 한다.
- **동결 경계**: P0 의 서빙 검증(T0 fixture, 길이·메모리·속도, B1 진입 조건)은 **합성 fixture 와 평가 풀 밖 문항**으로만 하므로 동결 전에 해도 된다. 평가 풀 문항이 모델에 들어가는 순간부터는 동결 후다.
- 문구는 **데이터 빈도와 업무 정의**로만 정한다. 수정 사유는 열거형만 허용: 지시가 두 가지로 읽힘 · 정답이 선택지에 없음 · 사전 등록한 빈도 바닥 · 스키마 한계(choice ≤255, score 2–10). "모델이 틀렸다" 는 사유가 아니다. 빈도 표는 라벨만 읽는 스크립트로 만들고, 그 스크립트에 모델 호출이 없어야 한다.
- 모델 출력이 생긴 뒤 문구를 바꾸면 그 분할은 폐기하고 남은 풀에서 다시 나눈다. 남은 풀이 없는 셋(FunctionChat 606 전부 사용, KorSTS·BoolQ·Belebele 등)은 다시 나누지 않고 **그 셋의 결과를 '탐색적' 으로 표시**한다. 시험 표본을 개발로 옮기지 않는다.
- **이미 본 것의 기록**: KoSGD 행동 목록(11종), `NONE` 비율, AFFIRM_INTENT·NEGATE_INTENT 를 진단으로 내린 근거(양성 68·78)는 10-12 에 시험 표본을 포함한 3,000 턴 전체의 라벨 집계로 정했다 (모델 출력은 보지 않았다). 그래서 감사의 '목록 밖 0 건' 은 독립 증거가 아니다. 진단 강등에 쓴 '빈도 바닥' 도 사전 등록이 아니었다 — 이 결정은 사후 결정으로 기록한다. 이후 시험 표본 라벨을 다시 보고 질문을 추가하지 않는다.

## 6. 서버 점유 절차 (GB10 · DGX Spark)

서버·시점은 **실행할 때마다** 정한다. 27B BF16 하나에 KV·작업 메모리까지 — 다른 큰 모델과 공존은 측정 전에는 하지 않는다.
두 서버는 GPUStack 이 관리하고 평가 레인이 돌 수 있다 (같은 서버에 벤치 동시 금지 — `RUNBOOK.md:316`). `start_eval_session.sh` 는 서버를 예약하지 않는다.

1. 진행 중 레인 확인 → 멈출 지점 결정. **`lane_guard.sh` 먼저 끄고** 레인 정지.
2. GPUStack 배포 상태 기록 → 인스턴스 정지 + 자동 재배치 방지 → GPU 메모리 해제 확인.
3. 결정 모델 컨테이너 기동 (한 번에 하나, 등록 순서대로).
4. 끝나면 컨테이너 정지 → GPUStack 배포 복구 → 기존 모델 smoke → 레인 재개 (`KRETA_RESUME=1` 등 기존 절차).

**다음 감사부터 적용할 규칙 (개정 12)**: 위 대체 규칙은 실패 원인을 따지지 않는다 — R5(행동 라벨 범위)·R7(행동 정답 연결)은 행동판에도 해당하므로, 그것이 실패하면 행동판은 대체제가 아니다. 앞으로는 **판마다 그 판에 해당하는 R2v3·R4·R5·R6·R7 을 모두 통과한 판만** 주 지표 후보가 되고, 전체판이 후보면 전체판, 아니면 행동판, 둘 다 아니면 멈춘다. 동결 때 문구를 다듬어 감사를 다시 돌리면 이 규칙을 쓴다.

## 8. 수용 조건

- **C1** `pytest jev_test/tests` 통과 — 세 갈래로 나눈다.
  - **지표**: 지표 함수가 손계산과 일치 (CP 상한·$b_{\rm flip}$·상태 판정 포함).
  - **분포 형식**: 분포 검증기가 NaN·음수·합≠1(§4-1 반올림 허용오차 밖)·질문/선택지 키 불일치를 거부. 선택지 매핑을 뒤집은 fixture 에서 **반드시 실패**.
  - **temperature 경로**: 분포 검증기로는 못 잡는다 (잘못 적용해도 정상 분포다). 실제 temperature 적용 함수에 고정 logit 을 넣어 기대 분포와 대조하고, 빼거나 두 번 적용하도록 오류를 주입하면 **반드시 실패**해야 한다. fixture 에는 차이가 드러나는 logit 구간(2지선다 logit 차이 $|z| \approx 1.55$ 에서 최대 0.0019. $z=0$ 이나 아주 큰 $|z|$ 만 있으면 차이가 거의 0 이라 못 잡는다)을 넣는다.
- **C2** T0 확률 대조 — 모델마다 fixture 전체에서 분포 최대 절대차·답 변경률이 P0 허용폭 이내.
- **C3** T0 공개 수치 회귀 — 선택한 Decision Index 벤치에서 공개 수치와의 차이가 P0 기준 이내 (키트 commit · edition 고정).
- **C4** 코호트 무결성 — 같은 논리 문항 ID 집합이 모든 모델에 요청됐고, 논리 요청 수 = ok + 실패 상태 합, 두 코호트 표가 모두 생성.
- **C5** 재현 지문 — 모든 결과에 모델 sha · 이미지 digest/의존성 버전 · 데이터 revision · 프롬프트 hash. 저장된 분포로 다시 채점한 값이 요약과 일치, 지문이 다른 결과를 resume 이 거부, 개발/시험·학습/평가 묶음 중복 0 건.

## 10. 범위 밖과 그 이유

| 뺀 것 | 이유 | 다시 볼 조건 |
|---|---|---|
| 결정 모델을 **리랭커**로 평가 | 이 평가의 질문(판단·보정)이 아니다. 27B 를 후보마다 돌리면 비용이 본시험보다 크다. `noul` 은 P(true) 하나만 돌려줘 포화되면 순서가 사라지고, 검색 정답은 미판정 문서를 비관련으로 쳐서 보정을 잴 수 없다 | 리랭커 교체를 실제로 검토할 때 (`reranker_test` 에 백엔드 추가) |

## 11. 남은 확인 (P0)

- Clef 실제 입력 상한 (카드 16,384 vs 블로그 64k) — 경계 근처에서 실제로 무엇이 잘리는지 (T0 긴 state fixture) · LBox 정답이 다중인지 · KoBEST 라벨 방향. (KoSGD active_intent 시점은 감사 v3 R6 으로 판정 끝.)
- 각 결정 모델 서버가 Clef 참조 구현처럼 4자리 반올림하는지, logit·log 확률을 따로 주는지 (진단 열용). 점수 1.0 동률 건수는 P0 에서 재지 않는다 — 평가 풀 출력이 필요하고, 계약은 이미 동결했다 (§4-1).
- B1 진입 조건 (§2-3): 실서버 vLLM 0.19.0 실효 설정, `top_logprobs=64`, 마스크 처리, chat 템플릿 답 위치의 단일 토큰.
- 운영에서 상한 초과 요청을 거절하는지, Clef 응답을 그대로 쓰는지 (§4-4 ③).
- 셋마다 라벨 출처(`label_source`): 생성·검수 방식. FunctionChat 시나리오 계보(원 시나리오 ID)가 있으면 연결요소 대신 그것을 묶음 키로 (출력 보기 전에만).
- 라이선스: KOLD·kor_unsmile(이제 미사용), WorkflowEvals 3종 데이터(HF 미기재), Decision Index 스위트 개별 조건, KoSGD (감사 예시 출력의 저장소 반입 여부).
- 개정 12 는 확정 전 새 세션 중재(10-13, `temp_result_1.md`)와 Codex 반박 2회를 합쳤다.
