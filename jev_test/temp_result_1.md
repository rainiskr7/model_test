### 나. 표본·통계

- **층화 표본 규칙** (Codex 1순위)
  - 층별 할당·가중치·뽑는 순서·20% 반올림이 없다. 그래서 상한이 어떤 모집단에 대한 95% 인지 말할 수 없다.
  - 인증용은 단순 무작위로 뽑고, 층화는 진단용으로 분리한다. 아니면 설계에 맞는 추론법을 명시한다.
- **상태 정의 보강**
  - `b_flip` 은 MEETS 일 때만 계산하고, 나머지 상태는 N/A 로 둔다.
  - NO_THRESHOLD 일 때의 결과 필드를 정한다.
  - "오류가 0이어도 인증할 수 없는 표본 수" 를 별도로 표시한다.
- **확신 점수 1.0 쏠림** (합의)
  - 이미 반올림된 확률은 log 로 바꿔도 복구되지 않는다 (log 1 = 0 한 점).
  - 반올림 전의 logit 이나 log 확률을 받는다. 확신 점수는 `−log(1−max p)` 로 계산한다 (나머지 선택지의 logsumexp 로 안정적으로 구한다).
  - 이 값은 max p 를 단조 변환한 것이다. 그래서 사전 등록한 $s_i$ 순서와 임계값 규칙은 그대로다.
  - **동률은 지금 규칙을 유지한다**: `s ≥ t` 면 동률 묶음 전부 수락, 위험 기준을 넘으면 NO_THRESHOLD.
    - 2차 키는 Codex·grok 이 모두 반대했다. 개발 표본에 규칙을 맞추는 효과가 있기 때문이다. Claude 도 2차 키 제안을 거둔다.
  - P0 에서 잴 것: 점수가 1.0 인 요청 수, 그 묶음의 오류율, 질문 유형별(noul·choice·score)·질문 수별 쏠림 비율.
  - **운영 재현성** (grok): 점수는 운영 API 가 주는 값으로 똑같이 계산할 수 있어야 한다. 평가에서만 log 확률을 쓰고 운영은 반올림된 확률만 받으면, 고른 임계값을 운영에서 재현할 수 없다.
- **pplx temperature 검사** (Claude·Codex)
  - temperature 가 1.00874 라서, 적용하든 안 하든 확률 차이가 최대 약 0.002 다 (Claude 계산).
  - 배치 변동으로 잡는 T0 허용폭보다 작을 가능성이 크다.
  - 그래서 코드 경로를 대조하는 단위 테스트로 검사하고, 분포 검증기(C1)와 분리한다. 분포 검증기는 정상 분포를 만드는 이 오류를 못 잡는다.
- **확인한 상태로만 쓸 것** (grok, 오독 정정): grok 은 "개발 기준(k/n ≤ τ/2)은 위험 보장이 아니다" 라고 했다. 하지만 계획은 이미 시험 표본에서 U ≤ τ 로 인증한다 (`:192`). 고칠 필요가 없다.

### 라. B1 (Qwen3.8-27B logprob 비교 기준)

- **확인**: B1 의 엔진은 vLLM 이다 (`foundation_model_test_non_thinking/configs/models/qwen_qwen3.8_27b.yaml:23`).
- **T2 제외** (합의)
  - T2 에서 빼는 것은 맞다.
  - 다만 이유는 "정확도 비교용" 이 아니다. **엔진이 다르고 부하 모양이 다르기 때문**이다 (B1 은 토큰 1개짜리 제한된 logprob 호출, T2 는 질문 묶음 요청).
  - `:68` 은 B1 을 "운영 대안" 이라고 적는다 → 아래 결정 1.
- **확인** (vLLM 0.19.0 공식 문서, [engine_args](https://docs.vllm.ai/en/v0.19.0/configuration/engine_args/))
  - `--max-logprobs` 기본값 20.
  - `--logprobs-mode` 기본값 `raw_logprobs`.
  - processed 값은 temperature·top_k·top_p 를 포함한 모든 processor 를 적용한 뒤의 값이다.
- **플래그**: `--logprobs-mode processed_logprobs --max-logprobs 64`. 기준은 KoSGD(39)가 아니라 **MASSIVE(60)** 다. 문서에는 "60 이상, 64는 여유" 로 적는다.
- **B1 사전 검증에 넣을 것**
  - 요청에 `logprobs=true` 와 `top_logprobs ≥ 선택지 수` (서버 상한만 올려서는 반환 개수가 늘지 않는다).
  - temperature=1, top_p=1, top_k 끔을 고정한다. processed 값에 이 처리가 반영되기 때문이다.
  - −9999 항목은 버리고, 맨 앞에 한 번 더 나오는 토큰은 ID 로 중복을 없앤다.
  - 모든 후보 라벨이 돌아왔는지, 재정규화한 합이 맞는지 확인한다.
  - chat 엔드포인트가 `top_logprobs=64` 를 받아들이는지 확인한다.
- **미확인**: processed 값의 상위 k 개가 `allowed_token_ids` 로 거른 뒤의 값인지.
  - 거르기 전이라면 일반 토큰이 자리를 채워 라벨이 빠진다.
  - 실제 서버에 시험 요청을 보내 확인한다. 그 전까지 "processed 가 필수" 라고 단정하지 않는다.
  - 안 되면 라벨 ID 별 raw 값을 받아 평가 코드에서 재정규화한다. 이때 후보 수만큼 호출이 늘 수 있다.
- **가장 먼저 막히는 곳** (합의): 라벨이 `A`~`Z` 라서 26개까지만 된다. 39개·60개용 단일 토큰 라벨 목록을 Qwen3.8 토크나이저로 정해야 한다. 플래그보다 이게 먼저 실패한다.

| 1. 잘림은 모순이 아니라 Clef 용 대리 기준, 명시만 하면 됨 | **판정 식에서는 맞음.** 다만 대리 기준과 원래 정의는 다른 사건을 본다. 문장은 이미 있으므로, 위 세 경우를 나눠 기록하고 운영에서도 같은 길이 검사를 둔다 | 맞음 + 보수적임을 명시 | 사건 구분 필요 | 사건 구분 + 운영 일치 |
| 2. 1.0 쏠림 → log 로 저장 + 동률 규칙 | **문제는 맞음.** 다만 반올림된 값의 log 는 소용이 없다. 반올림 전 logit/log 확률로 `−log(1−max p)` 를 계산하고, 동률은 현재 규칙(전부 수락 / NO_THRESHOLD)을 유지하며 P0 에서 쏠림을 잰다. 운영 API 가 같은 값을 줘야 한다 | logit 저장 (2차 키 제안 철회) | 반올림인지 과신인지 구분, 동률 쪼개기 반대 | 운영 재현성, 동률 쪼개기 반대 |
| 3. B1 은 정확도용이라 T2 제외, vLLM 플래그 필요 | **제외와 플래그는 맞음.** 다만 제외 이유는 엔진·부하 차이다 (`:68` 은 "운영 대안"). 플래그는 MASSIVE 60 기준, 요청 쪽 `top_logprobs` 와 processor 적용 순서는 P0 시험으로 확인한다. 라벨 26개 한계가 먼저 막힌다 | 맞음 + 사전 검증 항목 | 전제가 문서와 다름, 요청 쪽 설정 | 같음 + 60 기준 + processed 단정 보류 |
