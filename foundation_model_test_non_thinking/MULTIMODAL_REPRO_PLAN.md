# multimodal 재현성 검증 계획

러너나 채점 로직을 고친 뒤 **"채점이 바뀌지 않았다"를 증명하는 절차**다.
`MULTIMODAL_PUBLISH_CONTRACT.md` 가 "어떤 수치를 믿어도 되는가" 를 정한다면,
이 문서는 "코드를 고친 뒤에도 같은 수치가 나오는가" 를 정한다.

## 새로 만드는 것은 없다

초안에서는 `MULTIMODAL_BASELINES.json` 과 `verify_multimodal_repro.py` 를
신설하려 했다. **둘 다 폐기한다.**

- **기준선 파일이 필요 없다.** 기준선은 이미 `results/` 안에 있다 — 같은 코호트의
  기존 sidecar 가 곧 기준선이다. 별도 파일을 두면 산출물과 어긋나 조용히 낡는다.
  이 저장소가 이미 겪은 실패다 (`48bbdd5 보고 계층이 산출물에서 파생되게 —
  손으로 박은 측정값은 조용히 낡는다`).
- **별도 CLI 가 필요 없다.** "같은 것을 비교한다" 는 이미 `select.py` 의 코호트 키
  `(benchmark_id, variant, protocol.fingerprint, model_identity.canonical_id)` 가 하는 일이다.
  **한 코호트에 런이 둘 이상이면 그것이 곧 재현성 비교다.**

따라서 할 일은 **기존 도구를 고치는 것** 둘뿐이다.

---

## 1. 진단 — 지금 보고서가 깨져 있다

`gemma_4_26b_a4b_it` 이 K-DTCBench · K-MMBench · MTVQA-KR 표에서 **전부 빠져 있다.**
사유는 "동일한 최신 완료 시각 후보가 둘 이상" 이다.

원인은 이름이 아니라 **같은 런이 여러 벌 존재하는 것**이다. 실측:

```
results/gemma_4_26b_a4b_it/20260505_124246/.../k_dtcbench/results.json      sha 6dc272a1b708f59f
results/gemma_4_26b_a4b_it.bad/20260505_124246/.../k_dtcbench/results.json  sha 6dc272a1b708f59f
results/google_gemma_4_26B_A4B_it/20260505_124246/.../k_dtcbench/results.json sha 6dc272a1b708f59f
                                              완료 시각도 셋 다 2026-05-05T11:24:12.637171Z
```

바이트 동일한 복사본 셋이다. `select_representatives()` 가 동률로 판정해 자동 선정을
포기했고, 그 결과 주력 모델이 표에서 사라졌다. **게이트는 설계대로 안전하게
동작했지만, 결과적으로 유효한 측정이 유실됐다.**

추가로, 디렉토리명이 신뢰할 수 없다는 것도 확인했다:

```
gemma_4_31b_it/         -> 안에 든 model 필드: gemma_4_26b_a4b_it, gemma_4_31b_it
google_gemma_4_31B_it/  -> gemma_4_26b_a4b_it, gemma_4_31b_it, google_gemma_4_31B_it
```

한 디렉토리에 서로 다른 모델의 결과가 섞여 있다. **디렉토리명이 아니라 산출물의
`model` 필드가 진실이다.** 현재 sidecar 는 이미 `model` 필드를 쓰므로 코호트 자체는
올바르게 갈린다 — 이 부분은 고칠 필요 없다.

## 2. 고칠 것 — 두 가지

### A. 동일 런 중복 제거 (ambiguity 의 실제 원인)

코호트 안에서 **source-relative artifact role/path와 SHA-256 쌍의 집합**이 같고,
`counts`·`metrics`·`provisional` 측정 payload도 같으면 같은 런이다. 복사본이지
서로 다른 측정이 아니므로 하나로 접는다. SHA만 같거나 payload가 다르면 접지 않는다.

- 접을 때 남길 경로 우선순위: `.bad` 접미사가 없는 것 > 경로가 짧은 것 > 사전순.
  선택 근거를 sidecar 가 아니라 **보고서 각주**에 남긴다(원본 불변).
- payload가 같고 status만 다르면 `NATIVE`를 경로 우선순위보다 먼저 유지한다.
- 접은 뒤에도 후보가 둘 이상이고 완료 시각이 동률이면 기존대로 ambiguous 로 둔다.
- **SHA 가 다르면 절대 접지 않는다.** 서로 다른 측정이므로 그것이 곧 재현성 비교다.

이 하나만으로 gemma 가 세 표에 복귀한다.

### B. 모델 정체성 매핑 (새 런을 과거와 비교하기 위해)

같은 모델이 서빙 이름에 따라 다르게 기록된다:

```
gemma_4_26b_a4b_it          <- 과거 런 (서버 A)
google_gemma_4_26b_a4b_it   <- 2026-08-24 런 (192.168.0.7)
```

이대로면 새 런이 과거와 다른 코호트로 가서 비교가 안 된다.

- `configs/model_identity.json` 에 서빙명 → canonical id 매핑을 둔다.
- **매핑에 없는 이름은 추측하지 않는다.** 자기 이름을 그대로 canonical 로 쓰고
  보고서에 "미매핑" 경고를 남긴다. 다른 모델을 같다고 판단하는 것이 최악이다.
- sidecar 에 `model_identity` 를 추가하고 코호트 키의 `model` 을 이것으로 바꾼다.
  기존 `model` 필드는 서빙명 그대로 보존한다.

## 3. 코호트 안의 편차 = 재현성 지표

A·B 를 적용하면 한 코호트에 여러 런이 남는다. 보고서가 이를 드러낸다:

```
### K-DTCBench — full — protocol 4f3ddf31
| 모델 | 결과 | 상태 |
| gemma_4_26b_a4b_it | 206/240 = 85.83% | NATIVE |

> 재현성: 이 코호트에 런 2개. 코호트 산포 1건 (0.42%p), 허용 3건 — PASS
>   20260505_124246  207/240   (기준)
>   v2b_20260824     206/240   (대표)
```

### 허용 오차

temperature=0 이어도 서빙 비결정성으로 소수 건이 흔들린다. 실측:

```
PASS   max(정답 건수) - min(정답 건수) <= ceil(0.01 × 분모)
FAIL   그 외 — 보고서에 경고, --strict 에서 exit 1
```

| 벤치 | 분모 | 허용 | 실측 (2026-08-24) |
|---|---:|---:|---:|
| K-DTCBench | 240 | 3 | 1 ✅ |
| MTVQA-KR | 558 | 6 | 3 ✅ |
| KRETA | 2577 | 26 | 미측정 |
| K-MMBench | 4329 | 44 | 미측정 |

**항상 %p 와 건수를 함께 낸다.** 반올림된 %p 만 보면 표본 크기가 사라진다.
**protocol fingerprint 가 다르면 애초에 다른 코호트**이므로 편차 계산 대상이 아니다.
KOFFVQA judge의 `score/10`은 정답 건수가 아니므로 평균 점수의 코호트 산포를 비교한다.
허용치는 평균 `0.10/10`(전체 10점 척도의 1%)이다. 비교 축 누락, 분모 불일치,
미지원 단위는 성공으로 건너뛰지 않고 `비교 불가 — FAIL`로 기록한다.

## 4. 언제 무엇을 돌리나

전 벤치 재현은 약 3시간이다. 매번 돌릴 수 없으므로 나눈다.

### quick (~15분) — 러너를 고칠 때마다
```
K-DTCBench  240   ~4분
MTVQA-KR    558   ~10분
```
서로 다른 채점 경로 둘을 덮는다 — 객관식 추출(`_choice`)과 다중 gold 매칭(`_mtvqa_match`).

### full (~3시간) — 채점 로직을 건드렸을 때
```
quick             ~15분
KRETA direct 2577 ~70분   <- 독립 parser 경로
K-MMBench    4329 ~80분   <- 최대 표본
KOFFVQA       275 ~5분    <- UNSCORED 경로
```

**KOFFVQA 는 점수가 아니라 상태를 본다** — `UNSCORED` + `publishable=false` +
**exit 0** 이어야 한다. 채점이 없는 것과 실행이 실패한 것은 다르다.

| 변경 | 필요한 단계 |
|---|---|
| `publish/report.py` 만 수정 | 불필요 (pytest + derive 재생성으로 충분) |
| `publish/adapters.py` 채점 로직 | **full** |
| `benches/*.py` 러너 | **quick**, 채점부를 건드렸으면 full |
| 새 벤치 추가 | 해당 벤치만 |
| 모델/서빙 설정 변경 | 재현성 검증이 아니다 — 새 측정이다 |

---

## 5. 실행 규칙

1. **같은 서버에 벤치를 동시에 걸지 않는다.** 2026-08-24 에 세 벤치를 한 서버에
   동시 실행했더니 KRETA 가 워커 4개로 점유해 나머지 둘이 24분간 0건을 처리했다.
   서버를 나누거나 순차로 돌린다.
2. **기준선이 있는 모델로 돌린다.** 서버에 다른 모델이 올라가 있으면 재현성 검증이
   아니라 새 측정이다. 섞지 않는다.
3. **`EVAL_TIMESTAMP` 에 `repro_` 접두사**를 붙여 정식 측정과 구분한다.
4. KRETA 는 `--limit` 이 없다. 전량 2577건이므로 quick 에 넣지 않는다.

## 6. 아직 못 하는 것

- **B-3 구조화출력**: `data/structured_output/` 이 사내 이미지라 이 저장소에 없다.
  기존 산출물 7개가 전부 `total=0` 이라 기준선도 없다. 데이터가 있는 환경에서
  따로 세워야 한다.
- **KOFFVQA 판정 축**: 판정기를 고쳤지만 실제 채점을 돌린 적이 없어 기준선이 없다.
  한 번 돌려 고정해야 `judged` 축의 재현성을 볼 수 있다.
- **KRETA `default` 모드**: 응답이 길어 훨씬 느리다. 기준선은 있으나 재현 비용이 크다.
  `direct` 로만 정기 검증하고 `default` 는 필요할 때만 본다.
- **B-4 latency 재현성**: 정확도 건수 규칙을 적용할 수 없고 condition·percentile별
  허용 정책도 아직 검증하지 않았다. 운영 지표 자체는 계속 발행하지만 재현성
  `--strict` 대상에서는 제외한다. 정책을 정하기 전에는 full 단계에도 넣지 않는다.
